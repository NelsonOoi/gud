# gud v1 real-agent evals: git vs gud1-cc vs gud1-ref (2026-10-20)

Three coordination-forcing specs × three arms × N=4 agents × 2 trials, plus a smoke of each new arm on
`todo-cli` at N=2. All runs used `claude-sonnet-5-5`, a $1.20 run budget ($0.30 per agent), a 20-minute
timeout, and the gud v1 code at `v1` 71ca059 (the integration merge) driven through the real `gud1` command
line: `host serve`, `tester`, `mcp` and `agent`. The harness is in `evals/v1/` (see its README, section "gud v1
arms"). Raw transcripts are kept locally and not committed. Each run's `summary.json` is under
`runs/20261020-v1-grid/` and `runs/20261020-v1-smoke/`.

**Spend: $14.01 of the $30 cap**, recorded in `runs/v1-spend.json` and enforced by `cap.py`:

| batch | runs | $ |
| --- | ---: | ---: |
| smokes before the integration merge (`runs/20261020-v1-smoke-preintegration/`) | 2 | 0.40 |
| grid before the integration merge, stopped when the coordinator asked for the merge (`runs/20261020-v1-grid-preintegration/`) | 9 completed + 3 interrupted | 5.38 |

## What the numbers show

1. **The hidden tests don't separate the arms.** All 18 runs passed every hidden test, including the three
   refactor-guard guard tests. The repo's own tests passed on every final tree. At N=4, Sonnet 5.5 is at the
   ceiling on these specs, so on hidden-test pass rate the comparison is a tie. That says nothing either way
   about larger N or harder specs.
2. **The context check passed in every arm.** In all six refactor-guard runs at least one agent read
   `notes/cleanup.py`, which the task never names, and the final tree fixed its `NOTE_FILE` guard (the naive
   fix in `hidden/refactor-guard/naive/` fails exactly the three guard tests). Three or four agents per run read
   the guard. In the reference arm all four agents read it in both trials, and the three non-holders read it
   only to warn the holder in comments. Agents read beyond their own files in every arm: 3.6 (git), 3.6
   (gud1-cc) and 5.9 (gud1-ref) reads per agent outside the files they changed on refactor-guard, and 4.1,
   5.0 and 5.5 on acme-site-shared. todo-stack was written mostly from scratch, at 0.1–1.4 reads per agent.
3. **gud1-ref was cheapest and fastest because one agent did all the work.** In all six runs, one reference
   agent claimed T1 with scope `**` and shipped the whole spec in one push. The other three saw that T1 was
   held and, following their prompt ("Do not claim what someone else holds"), did nothing more. The exception
   was refactor-guard, where they posted review comments (2–3 per run) pointing at the `gc` guard. The holder
   never posted subtasks. So $0.22–$0.30 and 83–152 s per run measure one agent working alone with three
   observers. They don't show a coordinated swarm.
4. **gud1-cc agents did coordinate, but not with the v1 primitives built for it.** Exactly one claim won per
   run, always on T1, with 0 claim updates, 0 releases and 0 subtasks in all six runs. There were 0 claim
   overlaps, so overlap settlement was never exercised. The other agents worked unclaimed (claim scope is
   advisory) and talked in `comment`s on T1 (2–4 per run). They called `inflight` 0–7 times per run (5–6 on acme-site-shared, 5–7 on todo-stack, 0–2 on refactor-guard).
   - On todo-stack, the four agents split library, CLI, API and docs in comments. Four distinct authors landed
     four links in each trial (one of them carried onto a newer tip), with 0 colliding pushes.
   - On acme-site-shared t1, two agents built the same shared nav, `build.py` and stylesheet. One push was
     superseded, two more were refused before sending (stale base), and that agent dropped its work. In t2,
     the claim holder took `**` and the others deleted their drafts.
5. **gud1-cc wall time is mostly idle waiting.** It ran 2.5× git's wall time on todo-stack and 4.9× on
   refactor-guard, at similar or lower cost ($0.40–$0.56 against $0.52–$0.69). In every gud1-cc cell, 1–2
   `wait` calls timed out after 300–600 s. Agents without a claim waited for `linked` or `review.requested`
   events that, under the event concern rules, never reach them (gud issue 2 below). The agents doing the work
   finished in 20–100 s.
6. **git agents duplicated more work.** Git runs left 1.5–4 PRs unmerged per run: competing full-site or
   full-feature PRs that the agents then asked each other to close. In gud1-cc that waste shows up as 0–3
   superseded or refused pushes per run, plus drafts the agents deleted after seeing `inflight` or comments.
   Those drafts aren't counted, so the two numbers aren't directly comparable. On refactor-guard every arm
   landed exactly one author's change.
7. **Not exercised:** objections (0 in every run, reason-only or evidence), consent escalations and task
   escalations (0), red tips (0 episodes; every tip test passed, so no time to green), claim overlaps (0) and
   fix tasks (0). `review.requested` fired 0–3 times per gud1 run (rewrites of lines other agents had written
   moments earlier) and each window closed by lazy consensus. Under the `tip` test policy no push waited for a
   test. Test runs per link were 1.4–3.0; on single-link runs that figure includes the genesis tip run and the
   acceptance run. So nothing here supports a claim about consent v1, deadlock handling or red-tip recovery.

## Transcript analysis: coordination before colliding pushes (gud1-cc)

A push "collides" when another agent's push touched one of its files and neither was in the other's base.

| --- | --- | --- | --- | --- |
| acme-site-shared | 1 (0–2) | 1 (0–2) | 1 (0–2) | 2 (2–2) |
| todo-stack | 0 | — | — | 0 |
| refactor-guard | 1 (0–2) | 0 | 0 | 0 |

In the one refactor-guard collision (t1), @a1 and @a2 both implemented all four features. @a2's claim on T1
won and @a1's was lost. @a1 then pushed 11 s after @a2, without calling `inflight`. Its push was
superseded, and @a1 synced and stopped. In the acme-site-shared collisions both agents had called
`inflight` and commented first, but they announced the same shared files at about the same time.

"Reads outside the claimed scope" (2nd table below) is high for gud1 mostly because 3 of 4 agents per run held
no claim, so every file they read counts as outside their claimed scope. For claim holders the figure was 0 in
11 of 12 runs, because they claimed `**` or their whole slice.

## gud issues found (gud source not changed)

1. **Derived `task.done` fires on the first link of an unsplit task.** Module: `gud/core/tasks.py` (derived
   done, SPEC-v1 §16.6: "work done … a link with `Gud-Task = X` exists"). Repro: open T1 with an `accept`
   command that already passes on the seed, for example `python -m pytest -q`. Have any member push one
   unrelated file with `task=T1`. T1 becomes `work_done`, the tester's acceptance run passes, and T1 is
   `done`. Evidence: in `todo-stack` gud1-cc t2, T1 was `done` at 28.5 s after a README-only link by @a4,
   while the library, CLI and API landed at 38 s, 162 s and 365 s. In `acme-site-shared` gud1-cc t1, T1 was
   done at 58.8 s and the Home and Features pages landed at 336 s. In every gud1 run T1 was done after the
   first link. The criteria here are weak (the visible test suite), but the rule itself means a task's
   "done" says nothing about its scope unless the holder splits it. Agents treat "T1 is done" as "nothing
   left to do" (several gud1-cc final messages, and every reference agent once T1 was done).
2. **An agent with no claim and no live push can never be woken by other agents' links.** Module:
   `gud/core/replay.py` `_linked_concerns` (SPEC-v1 §19.2 `linked` concerns: author, holders of overlapping
   claims, authors of live pushes on the same files). The MCP `wait` tool (`gud/mcp_v1.py`) only returns
   journal events. Repro: @a1 claims T1 with `files=["todo.py"]`, @a2 holds nothing. @a2 calls
   `wait(timeout=300, types=["linked"])`, @a1's push links, and @a2's wait times out ("nothing new"). Evidence:
   `refactor-guard` gud1-cc t1 @a4 (wall 635 s, a `wait` timed out at 600 s), t2 @a2 and @a3 ("I waited 5 minutes
   for a review request or a landed link, and none arrived"), and 1–2 such timeouts in every gud1-cc cell. This
   is consistent with the spec, but it gives unclaimed members no way to follow the repo except polling
   `log` or `status`. It inflated gud1-cc wall time by roughly 300–550 s per cell.
3. **The reference agent never splits, so N agents behave as one.** Module: `gud/agent/prompt.py` together
   with leaderless claims (one active claim per task, §16.3). The prompt says "If a task is big and you hold
   it, split it into subtasks". In all six grid runs (and both smokes) the holder judged the task small,
   claimed `**`, and the others stood down. This is a behaviour finding about the prompt and protocol
   together, not a crash. Whether gud1-ref can parallelise at all needs a task the holder will actually
   split, or a planner.

No crashes, tracebacks or tester errors appeared in any host, tester or runtime log of the 18 runs. One harness
bug was found and fixed: the acme-site-shared hidden test required `<a class="cta">` but every arm wrote
`<section class="cta"><a href="pricing.html">`, a fair reading of the spec. The pre-integration acme runs were
rescored (27→28).

## Limitations

- Two trials per cell at N=4 only. Ranges are wide and the cells are small, so read differences of less than
  about 1.5× in wall time or cost as noise.
- Local transports only: a git bare repo, and gud over a FakeMailbox root with an HTTP host on localhost.
  There are no email delays.
- gud1-ref has its own system prompt and gets the task from the board rather than the shared preamble, so it
  differs from the other two arms in prompt as well as in coordination layer. Its token count is the
  runtime's ledger metric (cache reads at 1/10), so it can't be compared with the Claude Code arms' tokens.
  Its cost is SDK-reported, like the others.
- The `tip` test policy means gud1 pushes never wait for tests, while every git merge runs the suite. Neither
  arm ever landed a failing tree here.
- Pre-integration runs (`*-preintegration/`) used the earlier local-host wiring. They are kept for reference
  and are not in the tables. Their 9 completed cells show the same pattern: 100% hidden tests after rescoring,
  gud1-ref with a single `**` holder, gud1-cc with one claim and coordination in comments.
